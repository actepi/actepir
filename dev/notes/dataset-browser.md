# Dataset Browser

`episerver_browse()` opens the Dataset Browser, formerly the EpiServer Browser. Analysts use it to find a database, schema, table or view on EpiServer, read its columns with their labels, and copy the R code that reads the table. It is opened from Addins > Open Dataset Browser or by calling `episerver_browse()`. Pull request 1 rebuilt it to `dev/reference/app-style.md` and taught it to read the new label table, `ref.DataProperties`. Its labels will also make the full data dictionary planned in `dictionaries.md`.

## Decisions

- **Order in which label tables are tried.**
  - First `ref.DataProperties`, then today's order unchanged: tables named `DataLabels` (`ref` before other schemas, then by schema), then `DataLabelsNew` (the same), then other tables whose name holds DataLabels.
  - DataProperties is only looked for in the `ref` schema (the maintainer's decision).
  - Label tables may be tables or views, because sqldta's example builds `ref.DataProperties` as a view over the old table.
  - A label table is offered only if it has every column of its layout. DataLabels tables still need `DataType`, as before, although it is not read.
- **Fallback for each table.** A table takes its labels from the first label table, in that order, that holds rows for it (`.lbl_sql_pick()`: one `CASE WHEN EXISTS` query).
  - sqldta (`w4rhol/sqldta`) instead falls back only when the label table does not exist. The maintainer agreed to differ, for two reasons. Labels will move to DataProperties table by table. And sqldta's view (`examples/data_properties_view.sql`) files label sets that are not mapped under `dbo` only, so tables in other schemas would lose labels they have today.
  - During the move, R and Stata may therefore show different labels for a table.
  - The Table list follows the same rule: a table's dataset label comes from the first label table that holds any rows for it, even if that one has no dataset label and a later one has. Otherwise the list and the description on the Collection tab could show different labels for one table. `.lbl_sql_dataset_labels()` gets this in one query: each label table's dataset labels for the schema and, for every label table but the last, the names of the tables it holds rows for (`SELECT DISTINCT`, which an index on the name can serve). `.lbl_dataset_labels()` then takes each table's label in R. The parts of the `UNION ALL` take `COLLATE DATABASE_DEFAULT`, so that label tables of different collations do not conflict.
- **The two layouts,** as in sqldta's `docs/setup.md`:
  - DataProperties: `TableSchema`, `TableName`, `ColumnName`, `PropertyType`, `PropertyCode`, `PropertyText`, matched by schema and name with `N'...'` literals.
  - Since plan pull request 10, a DataProperties table may also have `PropertyTheme` and `PropertyThemeOrder` (`.lbl_themes`). On 28 Oct 2026 the maintainer made `Analysis.ref.DataProperties` a table rather than a view, with these columns, to serve more than sqldta: `TableSchema` varchar(5) and `TableName` and `PropertyType` varchar(32), not NULL; `ColumnName`, `PropertyCode`, `PropertyTheme` varchar(32); `PropertyText` varchar(4000); `PropertyThemeOrder` int. `.lbl_sql_sources()` says in Themes whether a DataProperties table has both theme columns, and `.lbl_sql_rows()` reads them only then, so a DataProperties table without them, in another database or before the change, is offered and read as before. The themes are read for every row, but only dataset notes use them. `.lbl_normalise()` gives every row Theme ("" without one) and ThemeOrder (NA without one).
  - DataLabels: `Dataset`, `VarName`, `LabelType`, `DataCode`, `LabelName`, matched by table name only, with plain literals.
  - Types are read in any case. `Opt`, `Var`, `NoteVar`, `NoteDta` and `DtaLabel` map to ValueLabel, VariableLabel, VariableNote, DatasetNote and DatasetLabel. `DataLabel` (sqldta 1.0.0) maps to DatasetLabel. `DatasetDescription` (plan pull request 10) is read as itself: the maintainer has filled it in for the tables of `Analysis`, a paragraph to a row, ordered by PropertyCode. Scripts take variable and value labels alone, so the new type does not reach them.
  - VariableFormat (Stata display formats) is not read.
  - Duplicates keep the first row, as `applydatalabels()` does.
  - Notes with codes come first, in code order (numerically when every code of the column's notes is a number), then the rest in row order, as sqldta applies them. The paragraphs of a dataset description take the same order. Dataset notes are first put in the order of their themes: each theme by its least PropertyThemeOrder, then themes without an order by name, then notes without a theme; within a theme, by code (`.lbl_table()`, which gives `note_themes` beside `notes`). The maintainer's themes on 28 Oct 2026 were, in order, General, Access and use, Collection methods, Weighting and survey design, Comparability, Key variables and Data quality, and more may be added; nothing in the code names them.
  - Value labels are sorted numerically first, then as text.
  - Column names are matched to label rows in lower case, as SQL Server matches names.
- **Value labels are read only when shown** (`.lbl_sql_rows(values = TRUE)`), because a table can have many thousands. The other rows are read when a table is chosen. Show value labels is on by default (the maintainer's choice, 26 Oct 2026), so a table's value labels are read when it is chosen unless the analyst turns them off.
- **Name.** The app is "Dataset Browser" and the add-in "Open Dataset Browser", which keeps the add-ins' "Open <tool>" pattern (the maintainer's choice). `episerver_browse()` and `episerver_browse_stop()` keep their names. `episerver_browse()` passes `...` to `episerver_connect()`, documented with `@inheritDotParams episerver_connect encrypt trust_certificate`, as CLAUDE.md requires and `episerver_dsr()` does. `episerver_dsr()` inherits its parameters from `episerver_browse()`, so they stay documented there.
- **Tables and views** are both listed. Label tables (names holding DataLabels, `DataProperties` and sqldta's `DataPropertyTables`) are left out, in every schema.
- **Layout,** as built:
  - bslib `page_navbar()` with `.epi_theme()`, `.epi_app_style()` and the actepir lockup at the right. No Done button: `.epi_stopped_script("Dataset Browser", "Open Dataset Browser", "episerver_browse")` and, in the foreground, `session$onSessionEnded(shiny::stopApp)`.
  - Sidebar, 340px and resizable, in accordion sections that start open:
    - Dataset: Database (Analysis by default; system databases and those starting with an underscore hidden, as before), Schema (dbo by default), and a searchable Table list. Each option shows its dataset label: the label goes in the option text after a tab, and a selectize render function shows it muted (`.browse-label`, lighter on the chosen option's Nightshade). Tables and views are grouped. The table chosen stays chosen when the list changes and still holds it; otherwise the first table is chosen.
    - Labels: Labels table (Automatic by default, or any label table found) and Show value labels. A label table chosen in another database counts as Automatic until the list is updated.
    - The information button on Labels table holds its notes.
  - Foot (`.epi-actions`): `.epi_bug_button()` alone. Copy Code and Download were here, under a third section, Code, until plan pull request 7 moved them to the Columns tab.
  - Tabs: Tables, Columns, Profiler, Collection, Var Finder and Help, and the browser opens on Tables. The maintainer placed the Profiler after Columns (26 Oct 2026). The maintainer chose the order and the name Var Finder after their test on 26 Oct 2026; the tabs were first Columns, Collection, Tables, Search and Help, opening on Columns. The Var Finder tab's value and inputs keep the names `search` and `search_*`. The Help tab uses the shared `.help` style, moved from the DSR Calculator to `.epi_app_style()`; its sections are Finding a table, Tables, Columns, Copying code, Dictionaries, Profiler, Collection, Var Finder, Where labels come from and Reporting a problem, in the order of the tabs. The maintainer asked for it to be rewritten in proper, easy-to-read English (27 Oct 2026): it now speaks to the analyst ("you"), in shorter sentences, with lists where it lists things, and its sections follow the tabs.
  - Info bar: the table, whether a table or a view, and its number of columns; where its labels came from (`.browse_labels_note()`), naming the earlier label tables that hold none for it; or that no label table holds labels for it, or that the database has none.
  - Read errors: a failure to read the tables or the columns makes the info bar an error (`epi-error`); a failure to list the databases or label tables, or to read the dataset labels, the labels or the value labels, adds a warning (`epi-warn`) and the rest is still shown.
  - The Collection tab (`.browse_about()`), as the maintainer asked on 27 and 28 Oct 2026 (plan pull requests 9 and 10): the dataset label as the heading (`h4`), or the table's full name, such as Analysis.dbo.APC, when it has none; then Dataset description (`h5`), a point for each paragraph, or "No dataset description available for this collection."; then Dataset notes (`h5`), the notes as points under a heading for each theme (`h6`, in Iris), or as one list when no note has a theme, or "No dataset notes available for this collection."; then, when the table has any, Linked tables (`h5`), a point for each. Notes without a theme come last, under Other, when other notes have themes. Linked tables have no line of their own when there are none, as few tables have any. Before plan pull request 9, the tab gave the label, the notes and a line on linked tables with no headings, or said the table had none of them. They were first shown above the column table, as sqldta's dialog shows them; the maintainer moved them to their own tab (26 Oct 2026), because some tables have many notes on the history of a survey or collection, which pushed the columns to the bottom of the window. Few tables have a description; more have notes. The tab was first called Dataset notes, with the number of notes in its title, as "Dataset notes (3)"; the maintainer chose the name Collection and a title without the number.
  - The Columns tab's own panel (`.epi_tab_settings("columns_settings", ...)`), since plan pull request 7: Connection (quickconnect, connect or none, with its notes behind an information button), Declare packages and Import with labels, then Copy Code (Insert Code in the foreground) and the Download menu of the table's dictionary, with Dictionaries of all tables, which writes those of the schema or database to a folder (plan pull request 3, see `dictionaries.md`).

Of three ways offered (the tab's own panel; a split button and menus above the table; or keeping them in the sidebar and disabling them on other tabs), they chose the panel: it is the style guide's place for a tab's own settings, and leaves the settings in view. The table is narrower: at 1536 by 730, 892px wide where it was about 1,160px.
    - Dictionaries of all tables stays in the Download menu, so that every dictionary action is in one place (the maintainer's choice).

Expand and Collapse work in the page alone, with no round trip. The maintainer asked for all three on 26 Oct 2026.

The maintainer suggested it for columns with several notes (27 Oct 2026). Expand value labels and Collapse value labels do not open the notes.

## How to check a change

**Offline:** the three commands in CLAUDE.md; `Rscript dev/harness/run_app.R dev/harness/episerver_browser.js <out>/browse browse`, compared with the results in `dev/harness/README.md`, with its screenshots looked at; and `Rscript dev/harness/dryrun_live.R`, with and without `--without-dataproperties`.

**Against EpiServer:** the maintainer runs `testthat::test_local()`, in which `test-episerver_browse_live.R` and `test-episerver_getlabels_live.R` must run rather than skip. They then open the browser on:

- a table that has rows in `ref.DataProperties`;
- one that has rows only in `ref.DataLabels`;
- one that has rows only in `dbo.DataLabels`;
- a view;

and, for the same tables, compare the labels that `collect_withlabels()` applies with those the browser shows, with Labels table set to Automatic and to each label table that holds rows for the table, running the code the browser copies in each case.

For the Tables tab and the Var Finder tab (plan pull request 4), they open the Tables tab on `Analysis.dbo` and on another schema, note how long it takes to fill, compare a few rows with SSMS (rows, dates, the label table, the columns without labels), and click a table; then search for a column name, a variable label and a common value label such as "female", note how long each takes, and click a result in another schema.

For the Profiler (plan pull request 5), they profile a coded column, a text column, a date and a column of a large table, noting how long each takes, and compare a count or two with SSMS; choose a By column and try the three Show choices; check that a table's primary key and the columns matching the list are left out, change the list, save it, close the browser and open it again to see it kept, then restore the defaults; and open the DSR Calculator's Explore panel to check its spacing.

For the whole table's profile (plan pull request 6), they choose The whole table on a narrow table and on a wide one, note how long each takes, check a row or two against the one-column profile, sort by Codes without labels, click a column to profile it alone, and click Stop during a run on a large table.

For the Columns tab's panel (plan pull request 7), they open the Columns tab, check that the panel's settings change the code copied, that the Download menu's three items work and are not clipped, and that a column's notes open without choosing its row, at their usual window size.

For the Excel copy and the logo (plan pull request 8), they copy the dictionary of a table with codes such as 01 or 1-4, or labels that look like dates, paste it into Excel and check the cells are as written, and that a column's notes stay in one cell; then set a logo of their own in Dictionary logo, download a dictionary to see it, and go back to the lockup.

For the minor changes (plan pull request 9), they open the Collection tab on a table with a dataset label and notes, one with neither, and one whose notes have codes, and read the Help tab.

For the dataset descriptions and themes (plan pull request 10), they open the Collection tab on tables with descriptions and themed notes, check the order of the paragraphs, the themes and the notes in each theme against `ref.DataProperties`, and open a table of another database whose label table has no theme columns, if one exists.
